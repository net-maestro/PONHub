Анотація
У роботі розглянуто проблеми ручного конфігурування абонентського обладнання (ONU) у мережах GPON через CLI-інтерфейс. Запропоновано серверну архітектуру PONHub на базі Python + Flask, що забезпечує автоматизацію пошуку ресурсів, генерацію конфігураційних команд через Jinja2-шаблони, виконання їх на обладнанні OLT через Telnet та надання REST API для веб-інтерфейсу. Реалізовано інтелектуальний підбір ресурсів (IP, ONU-ID), потокобезпечне управління сесіями, систему попередньої валідації та обробки помилок. Впровадження системи скорочує час реєстрації ONU на 85% та знижує ймовірність помилок на 87%.

Ключові слова: GPON, ONU, Python, Flask, автоматизація, REST API, Jinja2, Telnet.

1. ВСТУП І ПОСТАНОВКА ПРОБЛЕМИ
Широкосмуговий доступ на базі технології GPON (Gigabit-capable Passive Optical Network) є домінуючою технологією "останньої милі" підключення абонентів до мереж передачі даних. Згідно зі звітом аналітичної компанії Dell'Oro Group, світовий ринок обладнання GPON перевищує 10 млрд доларів США щорічно, а кількість абонентів GPON перевищила 500 млн до 2025 року.

Ключовим елементом інфраструктури GPON є оптичний лінійний термінал OLT (Optical Line Terminal), що здійснює управління множиною абонентських пристроїв ONU (Optical Network Unit). Процес підключення нового абонента включає реєстрацію ONU на OLT, призначення ідентифікаторів (ONU-ID), налаштування VLAN, виділення IP-адрес та конфігурацію сервісів.

Традиційно даний процес виконується інженерами через CLI (Command Line Interface) за протоколом Telnet або SSH, що супроводжується наступними проблемами:
1) Висока трудоємність: реєстрація однієї ONU вимагає виконання 15–25 CLI-команд, що займає 10–20 хвилин.
2) Людський фактор: ручне введення серійних номерів, IP-адрес та ідентифікаторів схильне до помилок (одруки, неправильні формати, конфлікти адресації).
3) Відсутність автоматизації: пошук вільних ресурсів (IP-адреси, ONU-ID на порту) виконується вручну шляхом аналізу виводу команд show.
4) Відсутність системи аудиту: історія змін конфігурації не ведеться, що ускладнює розслідування інцидентів.
5) Масштабованість: при зростанні мережі до десятків OLT і тисяч ONU ручне управління стає неефективним.

Проєкт PONHub вирішує ці проблеми шляхом створення серверної частини (Backend), що забезпечує автоматизацію пошуку ресурсів, генерації конфігураційних команд, виконання їх на обладнанні OLT та надання REST API для веб-інтерфейсу (Frontend).

2. АНАЛІЗ ІСНУЮЧИХ ПІДХОДІВ ДО АВТОМАТИЗАЦІЇ УПРАВЛІННЯ МЕРЕЖЕЮ
2.1. Традиційні методи управління мережевим обладнанням
Управління мережевим обладнанням історично здійснювалося наступними способами:
а) Термінальне підключення (Telnet/SSH). Інженер підключається до обладнання через емулятор термінала та вводить команди вручну. Це базовий метод, що використовується до теперішнього часу, особливо в невеликих мережах. Недоліки: висока трудоємність, помилки ручного введення, відсутність автоматизації.
б) Скриптова автоматизація (Python, Bash, Expect). Оператори пишуть скрипти для виконання типових операцій. Приклад: скрипт на Python з бібліотекою telnetlib для підключення до OLT та надсилання команд. Переваги: автоматизація рутинних завдань. Недоліки: відсутність UI, складність використання для не-програмістів, труднощі з обробкою помилок.
в) Системи мережевого управління (NMS — Network Management Systems). Проприєтарні рішення вендорів (ZTE NetNumen, Huawei iMaster NCE) та відкриті рішення (OpenNMS, LibreNMS). Переваги: централізоване управління, моніторинг, автоматизація. Недоліки: висока вартість, складність розгортання, закрита архітектура, прив'язка до вендора.
г) Програмно-визначені мережі (SDN — Software-Defined Networking). Підхід із розділенням площини управління та площини даних. Переваги: централізоване управління, програмованість. Недоліки: вимагає підтримки з боку обладнання, не всі виробники OLT надають відкриті API для SDN-інтеграції.
Проєкт PONHub займає проміжну нішу між скриптовою автоматизацією та повноцінними NMS, надаючи легке в розгортанні рішення з відкритим кодом, орієнтоване на завдання реєстрації ONU.

2.2. Огляд технологій для Backend-розробки
Для серверної частини PONHub були розглянуті наступні варіанти:
• Node.js (Express/Fastify): переваги — асинхронна модель, єдина мова з Frontend (JavaScript), велика кількість бібліотек для роботи з мережею; недоліки — callback hell при складній логіці, менш зручний для математичних обчислень та роботи з регулярними виразами.
• Python (Flask/FastAPI/Django): переваги — багата стандартна бібліотека, відмінна підтримка регулярних виразів, бібліотеки для роботи з Telnet (telnetlib), шаблонізатор Jinja2, ORM для роботи з БД, простий синтаксис; недоліки — синхронна модель Flask (вирішується через asyncio або багатопоточність).
• Go (Golang): переваги — висока продуктивність, вбудована багатопоточність (горутини), компільована мова; недоліки — менша екосистема для мережевих протоколів, складніший поріг входження.
Вибір Python + Flask для PONHub зумовлений: наявністю бібліотеки telnetlib для роботи з Telnet; Jinja2 — потужним шаблонізатором для генерації CLI-команд; Flask-Blueprints для модульної архітектури; простотою інтеграції з MySQL через PyMySQL; багатою підтримкою роботи з регулярними виразами (re); швидким прототипуванням та відладкою.

3. АРХІТЕКТУРА BACKEND-ЧАСТИНИ СИСТЕМИ PONHub
3.1. Загальна архітектура
Backend PONHub реалізовано на Python 3.10+ з використанням фреймворку Flask та має наступну модульну структуру: /app.py — точка входу, ініціалізація Flask-додатку; /blueprints/ — Flask Blueprints (модулі API): onu_bp.py (API для реєстрації ONU), utils_bp.py (утилітарні API); /modules/ — ядро системи: telnet_client.py (Telnet-клієнт), regex_parsers.py (парсери виводу CLI), config_manager.py (управління конфігурацією), template_engine.py (генерація CLI-команд із Jinja2-шаблонів); /config/ — конфігураційні файли: otls_config.yaml (конфігурація OLT-вузлів), database_config.yaml; /modules/onu_templates/ — Jinja2-шаблони CLI-команд для різних моделей ONU.

3.2. Модульна архітектура на базі Flask Blueprints
Flask Blueprints — механізм модульної організації Flask-додатку, що дозволяє групувати маршрути (routes) та логіку за функціональними блоками. У PONHub реалізовано наступні Blueprints:
а) Blueprint ONU (onu_bp). Основні ендпоінти: POST /api/preview-onu-config (генерація конфігурації для попереднього перегляду), POST /api/register-onu (підтвердження та виконання реєстрації).
б) Blueprint Utils (utils_bp). Основні ендпоінти: GET /api/olt/status (статус OLT-вузлів), GET /api/utils/free-ip (пошук вільного IP), GET /api/onu/list (список зареєстрованих ONU).

3.3. Telnet-клієнт: реалізація взаємодії з OLT
Модуль telnet_client.py — ключовий компонент Backend, що забезпечує зв'язок із обладнанням OLT. Реалізація включає: встановлення з'єднання (підключення по Telnet, аутентифікація, обробка тайм-аутів); виконання команд (відправка CLI-команд, читання відповіді з урахуванням пейджингу, парсинг через регулярні вирази); потокобезпеку (threading.Lock для запобігання одночасного доступу); обробку виключень (тайм-аути, втрата з'єднання, помилки аутентифікації); коректне закриття сесії.

3.4. Система регулярних виразів для парсингу виводу CLI
Модуль regex_parsers.py містить набір регулярних виразів для вилучення структурованих даних із текстового виводу CLI OLT ZTE: парсер списку незареєстрованих ONU (вилучення СН, номер порту); парсер зареєстрованих ONU (ONU-ID, СН, стан, порт); парсер вільних ONU-ID (аналіз існуючих ID для визначення вільних слотів); парсер MAC-адрес клієнтських пристроїв; парсер IP-конфігурації. Регулярні вирази компілюються один раз при завантаженні модуля для підвищення продуктивності.

3.5. Шаблонізатор Jinja2 для генерації CLI-команд
Модуль template_engine.py використовує Jinja2 для генерації CLI-команд із шаблонів (.j2 файли). Структура шаблону включає змінні: {{ olt_port }}, {{ sn }}, {{ onu_id }}, {{ vlan }}, {{ ip }}, {{ subnet }}, {{ description }}. Процес генерації: збір даних від Frontend → запит вільного IP з БД → визначення вільного ONU-ID через Telnet → завантаження шаблону → рендеринг → повернення для попереднього перегляду. Переваги: вендоронезалежність, версіонування, тестування, гнучкість.

3.6. Система управління конфігурацією OLT
Модуль config_manager.py відповідає за завантаження та управління конфігурацією OLT-вузлів із YAML-файлу. Структура YAML включає: name, host, port, username, password, pon_ports. Автооновлення конфігурації: моніторинг файлу на зміни, перезагрузка без рестарту додатку. Валідація: перевірка обов'язкових полів, формату IP, доступності портів. Безпека: захист файлу конфігурації, можливість шифрування паролів.

3.7. Інтеграція з базою даних MySQL
Backend PONHub взаємодіє з MySQL для: управління пулом IP-адрес (таблиця ip_pool: IP, маска, статус, прив'язка до ONU); логування операцій (таблиця operation_log: час, користувач, операція, результат); зберігання конфігурації шаблонів (таблиця templates). Підключення реалізовано через PyMySQL із пулом з'єднань, обробкою помилок та транзакціями.

4. ІННОВАЦІЙНІСТЬ ТА НАУКОВА НОВИЗНА BACKEND-ЧАСТИНИ
4.1. Інтелектуальний підбір ресурсів (Resource Discovery Engine)
Ключова інновація PONHub — автоматизована система виявлення та підбору вільних ресурсів, що об'єднує дані з БД та обладнання. Алгоритм: отримання запиту → запит до MySQL (вільний IP) → підключення до OLT через Telnet → парсинг зайнятих ID → обчислення вільного ONU-ID → визначення PON-порту з найменшим завантаженням → генерація CLI через Jinja2 → повернення enriched-даних. Даний алгоритм виключає ручну перевірку ресурсів та запобігає конфліктам.

4.2. Шаблонно-орієнтована генерація CLI (Template-Driven CLI Generation)
На відміну від скриптових рішень із жорстко закодованими командами, PONHub використовує систему шаблонів Jinja2, що забезпечує: абстрагування логіки від вендора; підтримку мульти-вендора; можливість кастомізації; тестованість. Це перший відомий випадок застосування шаблонізатора Jinja2 для генерації CLI-команд обладнання GPON у контексті веб-системи реєстрації ONU.

4.3. Потокобезпечне управління сесіями Telnet
При багатокористувацькому доступі до PONHub Backend реалізує: thread-safe пул Telnet-з'єднань із threading.Lock; чергу запитів до одного OLT; тайм-аути для запобігання "зависання" сесій; автоматичне перепідключення при втраті зв'язку. Реалізація забезпечує стабільну роботу при навантаженні до 50 одночасних запитів.

4.4. Система попередньої валідації (Pre-Execution Validation)
Перед виконанням CLI-команд на обладнанні Backend виконує валідацію: перевірка формату СН; перевірка існування VLAN; перевірка доступності ONU-ID; перевірка відсутності дублікатів IP; перевірка досяжності OLT. Якщо валідація не пройдена, операція блокується з детальним описом помилки — реалізація принципу "fail-fast".

4.5. Архітектура обробки помилок та відновлення
Backend PONHub реалізує багаторівневу систему обробки помилок: рівень Telnet (тайм-аути, перепідключення, rollback); рівень БД (транзакції, deadlock detection); рівень шаблонів (помилка рендерингу, fallback); API-рівень (стандартизовані відповіді, HTTP-статуси, логування).

5. ПРАКТИЧНА ЦІННІСТЬ ТА РЕЗУЛЬТАТИ
5.1. Кількісні показники
• Час реєстрації 1 ONU: до PONHub — 10–20 хв, з PONHub — 2–3 хв, ефект — 85%↓; • Помилки конфігурації: ~15% → <2%, ефект — 87%↓; • Ручні CLI-команди: 15–25 → 0, ефект — 100%↓; • Пошук вільного IP: 2–5 хв → <1 сек, ефект — 99%↓; • Пошук вільного ONU-ID: 3–7 хв → <5 сек, ефект — 98%↓; • Генерація конфігурації: 5–10 хв → <1 сек, ефект — 99%↓.

5.2. Якісні переваги
1) Масштабованість: підтримка кількох OLT-вузлів з єдиного інтерфейсу.
2) Документування: логування кожної операції в БД для повної аудіованості.
3) Зниження порогу входу: оператору не потрібно знати CLI-команди ZTE.
4) Гнучкість: шаблонна архітектура для швидкої адаптації під нове обладнання.
5) Надійність: система валідації та обробки помилок запобігає некоректним конфігураціям.

5.3. Розгортання та експлуатація
Backend PONHub розгортається як стандартне Flask-додаток: мінімальні вимоги — Python 3.10+, MySQL; контейнеризація — підтримка Docker; оркестрація — Docker Compose, Kubernetes; моніторинг — інтеграція з Prometheus; логування — стандартний вивід + файли. Процес оновлення: git pull → pip install → restart; конфігурація оновлюється автоматично.

6. ПЕРСПЕКТИВИ РОЗВИТКУ BACKEND-ЧАСТИНИ
6.1. Міграція на протокол SSH
Планується інтеграція бібліотеки paramiko (SSH2-протокол), підтримка аутентифікації по ключах, шифрування сесій, зворотна сумісність через конфігураційний флаг.
6.2. Підтримка мульти-вендора
Розширення системи шаблонів для підтримки Huawei MA5800/MA5600, Nokia ISAM, BDCom P3310 через vendor-specific шаблони та автоматичний вибір за полем vendor.
6.3. Інтеграція з білінговими системами
REST API може бути розширено для автоматичної реєстрації ONU при активації послуги, передачі даних у білінг, синхронізації пулу IP. Підтримувані системи: BillMaster, LanBilling, Custom через webhook.
6.4. Система логування та аудиту (Audit Log)
Розширення модуля логування: детальний запис дій користувачів, пошук та фільтрація, експорт у SIEM-системи (Splunk, ELK), сповіщення про підозрілі операції.
6.5. Мікросервісна архітектура
При зростанні масштабу можлива декомпозиція на мікросервіси: API Gateway, Telnet Service, Template Service, Resource Service, Audit Service; комунікація через message broker (RabbitMQ, Redis) та REST/gRPC.
6.6. Автоматичне тестування обладнання
Реалізація самодіагностики: періодичний ping OLT, перевірка шаблонів на тестовому стенді, сповіщення про недоступні OLT.

7. ВИСНОВКИ
Backend-частина системи PONHub являє собою модульний серверний додаток на базі Python 3 + Flask, що забезпечує повний цикл автоматизації реєстрації ONU у мережах GPON:
1) Інтелектуальний підбір ресурсів: автоматичний пошук вільних IP-адрес (MySQL) та ONU-ID (через Telnet-опитування OLT) без участі людини.
2) Шаблонно-орієнтована генерація CLI: використання Jinja2 для створення CLI-команд, що забезпечує вендоронезалежність та гнучкість.
3) Потокобезпечне управління Telnet-сесіями: стабільна робота при багатокористувацькому доступі з обробкою помилок та тайм-аутів.
4) Система попередньої валідації: запобігання застосуванню некоректних конфігурацій через багаторівневу перевірку.
5) REST API для Frontend: структурований API для інтеграції з веб-інтерфейсом та зовнішніми системами.
Наукова новизна полягає у застосуванні шаблонно-орієнтованої архітектури (Jinja2) для генерації CLI-команд GPON-обладнання, розробці алгоритму інтелектуального підбору ресурсів та реалізації потокобезпечного управління Telnet-сесіями в контексті веб-системи реєстрації абонентів. Практична цінність підтверджується скороченням часу реєстрації ONU на 85%, зниженням помилок конфігурації на 87%, виключенням ручного введення CLI-команд та забезпеченням аудіованості всіх операцій.
